# Исправление пустых кабинетов AIU Campus Events

## Активация и предварительная проверка

Роль: senior-dev. Задача: реализация ролевых функций и исправление неполной первой поставки. Режим: локальная рабочая копия, сервер Next.js на 127.0.0.1:3002; без развёртывания внешней базы или публикации.

Прочитаны AGENTS.md, docs/PLAN.md, существующие auth.ts и dev-actions.ts, сервисы events/categories/comments/registrations/favorites/admin, валидаторы event/registration/favorite/category, связанные моки, admin-actions.ts, схема Prisma, макеты и навигация, документация установленного Next.js по серверным действиям. Проверены все вхождения PagePlaceholder и зависимости изменяемых сервисов.

Применены: аудит зависимостей, серверная авторизация, контракты данных, проверка сценариев и адаптивности. Пропущены: миграции PostgreSQL, внешние интеграции и production-деплой — они не настроены в исходном демо и не нужны для локальной проверки.

## 1. Результат и причина

Проверено по исходникам: пустые экраны были PagePlaceholder с одним заголовком. В первой поставке я оформил афишу и не проверил полноту каждого кабинета. Это мой недосмотр. Также старый мок регистраций содержал другие названия и даты событий под теми же ID, что афиша.

Теперь все ролевые страницы содержат рабочие сценарии. Общее локальное хранилище выбрано потому, что исходные сервисы были демонстрационными, а подключённой базы и готовой реальной авторизации не было. Файл сохраняет изменения между перезапусками; роль и принадлежность проверяются внутри серверных операций. Хранилище рассчитано на один процесс, а не на облачные экземпляры без общего диска.

## 3. Интеграционная проверка

- Импорты заменены; PagePlaceholder и конфликтующие моки удалены после поиска ссылок.
- Афиша, детали, регистрации, участники, посещаемость и статистика используют одинаковые события.
- Новое событие появляется в афише только после одобрения. Правка опубликованного события возвращает его на модерацию.
- Разделы закрыты по роли, серверные операции повторно проверяют пользователя и владельца записи.
- Студент получает QR с HMAC-подписью и короткий код; повторный чек-ин возвращает первую отметку без удвоения.
- Подсчёт мест согласован с подтверждёнными регистрациями. Отмена события снимает неиспользованные билеты.
- Данные .data, сессии, хеши и ключ QR исключены из Git, ZIP и трассировки сборки. Поля passwordHash/qrSecret не найдены в HTML проверенных страниц.
- Модель Prisma не менялась; внешние миграции не выполнялись.

## 4. Самопроверка

Разделены хранение, бизнес-правила, серверные действия и интерфейс. UI не определяет права самостоятельно. Совместимость используемых публичных сервисных контрактов сохранена, статусы расширены PENDING/REJECTED. Неиспользуемый старый декодер и заглушки удалены. Тесты проверяют бизнес-сценарии и независимо сгенерированные PNG, а не только форму реализации.

Сохранение полей проверено после ошибки окончания события: категория осталась cat-tech, название, описание, место и даты не пропали. Нормализация ранее отменённых событий исключает противоречие «подтверждено» при отменённом событии.

## 5. Доказательства проверки

Команды: npm test — 7/7 PASS; npm run build — PASS, TypeScript и Prisma generation выполнены, итоговая сборка без предупреждений.

Автотесты: запрет подмены роли и чужого события; модерация и обязательная причина отказа; конкурирующая запись без превышения лимита; продвижение очереди; проверка времени и статуса входа; повторный/чужой/неверный билет; пароль, сессия, блокировка; 20 различных реальных подписанных QR PNG декодируются обратно и принимаются сервером.

В браузере выполнено: организатор создал «Встреча AIU Campus Club — демо» → администратор одобрил → студент записался, добавил в избранное и оставил комментарий → QR появился в билетах → организатор проверил короткий код → вход сохранён → повтор показал «Участник уже отмечен», счётчик остался 1.

Дополнительно: создан тестовый аккаунт, сохранена группа AIU-QA-26, выполнены выход и повторный вход. Студент перенаправлен из organizer/new в no-access. Администратор нашёл созданного пользователя, назначил роль организатора (счётчик 3 → 4), затем вернул студента (4 → 3).

После остановки и повторного запуска сервера созданное событие осталось PUBLISHED, вход остался 1, группа профиля сохранилась. Повторный ввод билета после перезапуска вернул первоначальное время входа 02:59:21.

Мобильная ширина 390 px: форма организатора, сканер и пользователи — document.clientWidth = document.scrollWidth = 375 (15 px занимает полоса прокрутки). Переопределение viewport сброшено. Финальная форма не содержит ошибок в консоли.

HTTP-проверка подтвердила отрисовку кабинетов своих ролей и CSV владельца; CSV чужого события — 403. Для потоковых HTML-ответов Next.js отказ может идти внутри ответа HTTP 200: у гостя для PENDING-события присутствует NEXT_HTTP_ERROR_FALLBACK;404 без названия события, у студента для кабинета организатора — NEXT_REDIRECT на /no-access. Проверка только HTTP-кода не использовалась как доказательство доступа.

RCA QR: повторный прогон выявил нестабильность старого ZXing-детектора на случайных билетах. Целочисленный масштаб и TRY_HARDER отдельно не помогли; декодер заменён на jsqr для камеры и изображений. После замены серия из 20 разных PNG прошла. Исправление не подменяет настоящие QR рисунками.

Не проверено физически: конкретная камера устройства и разрешение браузера на неё. Камера не включалась автоматически. Проверены генерация, декодирование изображений общим движком и серверный ручной чек-ин. Локальный JSON-режим не является готовым production-бэкендом PostgreSQL.

## 6. Передача

Сборка и запуск: см. AIU-DESIGN.md. Для повторной проверки — npm test, npm run build, npm start. Камера требует пользовательского разрешения; если она недоступна, можно загрузить QR-изображение или ввести короткий код. Демонстрационные роли переключаются внизу справа.

ZIP содержит исходники, тесты, инструкцию и снимки интерфейса. Он не содержит node_modules, .next, .git, .data и временную папку work. После распаковки начальные демо-данные создаются заново; данные текущего локального просмотра остаются в его .data.

## Рефлексия и процесс

Находки: неполная проверка ролей, конфликтующие моки, сброс форм React и нестабильный QR-детектор устранены. Процесс: контракт → аудит зависимостей → реализация → проверка → исправление по RCA → повторная проверка → документация — выполнен. Все семь шагов SDID закрыты; автоматические тесты и браузерная проверка дополняют друг друга. В постоянную память записи не вносились: владелец этого не запрашивал.
