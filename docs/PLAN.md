# CampusEvents — план проекта и ТЗ

Афиша студенческих мероприятий: студенты находят события и записываются на них, организаторы создают события и проверяют вход по QR, админ модерирует.

> Как читать: раздел 1–2 — зачем и что делаем (ТЗ), 3–6 — как устроено технически, 7 — как выглядит, 8–9 — приоритеты и команда, 10 — роадмап из 7 этапов, 11 — задачи каждого участника по этапам с демо в конце каждого.
> Допущения, которые можно поменять: срок — 8 недель (подгоните под свой дедлайн), команда — 4 человека, работа каждого разбита на 7 этапов (раздел 10), «приоритеты посещения» = приоритетная запись на события (раздел 5).

---

## 1. О проекте

### Проблема
Информация о студенческих мероприятиях разбросана по чатам, афишам и сторис. Организаторы не знают, сколько людей реально придёт, а студенты не знают, остались ли места. Записи «для галочки» занимают места, а потом люди не приходят.

### Решение
Единая афиша с записью, лимитом мест, честным входом по QR и приоритетом для тех, кто действительно ходит на события.

### Роли
| Роль | Что делает |
|------|------------|
| Гость | Смотрит афишу и страницы событий, регистрируется |
| `USER` (студент) | Записывается, отменяет запись, добавляет в избранное, комментирует, показывает QR на входе |
| `ORGANIZER` | Создаёт события, видит участников, сканирует QR на входе, настраивает приоритетное окно |
| `ADMIN` | Модерирует события, управляет категориями и ролями, видит статистику, удаляет комментарии |

### Главные сценарии
1. **Студент:** открыл афишу → нашёл событие по фильтрам → записался → получил QR в «Моих регистрациях» → пришёл, показал QR → посещение засчитано.
2. **Организатор:** создал событие → оно ушло на модерацию → после одобрения открыл запись → в день события сканирует QR у входа → видит, кто пришёл.
3. **Админ:** увидел очередь модерации → одобрил или отклонил событие → следит за статистикой.
4. **Приоритет:** студент, который регулярно приходит, получает статус «Активный» и записывается на популярные события раньше остальных.

### Вне рамок (не делаем)
Оплата билетов, нативное мобильное приложение, чаты между пользователями, подтверждение почты через внешние сервисы (если не хватит времени — см. «Если останется время»).

### 2.2. Нефункциональные требования
- Три роли строго разделены: закрытые страницы закрыты через `proxy.ts`, и такие же проверки есть внутри каждого API (одной защиты страниц недостаточно).
- Вся валидация пользовательского ввода — Zod, на клиенте и на сервере одной и той же схемой.
- Лимит мест и приоритетная очередь работают корректно при одновременных запросах (транзакции).
- Сайт удобен на телефоне: основной сценарий студента и сканер QR проверяются на смартфоне.
- У каждого экрана есть состояния: загрузка, пусто, ошибка.
- Пароли не хранятся в открытом виде (обеспечивает Better Auth); секреты — только в переменных окружения.

## 3. Технологии и архитектура

### Стек
- Next.js (App Router), TypeScript, Tailwind CSS
- PostgreSQL + Prisma, валидация — Zod
- Аутентификация — Better Auth
- Защита маршрутов — `proxy.ts` (в Next.js до 16 версии назывался `middleware.ts`)
- Формы — React Hook Form + Zod resolver (предложение)
- Компоненты — собственный UI-кит на Tailwind; можно взять за основу shadcn/ui (предложение, решается на Этапе 1)
- QR: генерация — `qrcode`, сканирование камерой — `@yudiel/react-qr-scanner` или `html5-qrcode` (предложение, проверить на телефоне)
- Деплой — Vercel + Neon или Supabase

### Структура папок (договариваемся на Этапе 1)
```
src/

    (auth)/          вход, регистрация
    (public)/        афиша, страница события — шаблон для студентов и гостей
    (student)/       мои регистрации, избранное, профиль
    (organizer)/     кабинет организатора: события, участники, сканер
    (admin)/         админ-панель
    api/             Route Handlers
  components/
    ui/              UI-кит (кнопки, поля, карточки, модалки)

    mocks/           тестовые данные для фронта
  proxy.ts
prisma/
  schema.prisma
  seed.ts
```

### «Сначала фронт, потом бэк» — как это работает технически
Чтобы фронт мог идти без готового бэка, весь доступ к данным идёт через **слой сервисов** `lib/services/*`:

1. На Этапе 1 каждый владелец модуля описывает функции своего сервиса и Zod-типы, например `getEvents(filters)`, `registerForEvent(eventId)`.
2. На Этапах 2–3 эти функции возвращают данные из `lib/mocks` (с искусственной задержкой 300–600 мс, чтобы видеть состояния загрузки, и с возможностью вернуть ошибку).
3. На Этапах 4–5 владелец модуля пишет реальную реализацию на Prisma с той же сигнатурой.
4. По мере готовности модуля мок отключается переключателем (общий `NEXT_PUBLIC_USE_MOCKS=false` или свой на модуль), страницы почти не меняются.

Правило: компоненты и страницы **никогда** не импортируют моки напрямую, только сервисы. Это и есть контракт между фронтом и бэком.

## 4. Модель данных

Дополнения к исходной модели выделены словом «новое».

- **User** — роль: `USER` / `ORGANIZER` / `ADMIN`; новое: `priorityStatus` (`STANDARD` / `ACTIVE`), `attendedCount`, `noShowCount`
- **Category** — название
- **Event** — название, описание, место, `startsAt`, новое: `endsAt`, лимит мест, статус (`PENDING` / `PUBLISHED` / `REJECTED`), причина отказа (новое), организатор, категория; новое: `registrationOpensAt` (общая запись), `priorityWindowHours` (на сколько часов раньше открывается запись для приоритетных; 0 = окна нет)
- **Registration** — пользователь + событие, пара уникальна; новое: `status` (`CONFIRMED` / `WAITLIST` / `CANCELLED`), `createdAt`, `qrToken`, `checkedInAt`, `checkedInById`
- **EventPriorityMember** (новое, P1) — событие + пользователь: организатор вручную даёт приоритет, например членам своего клуба
- **EventStaff** (новое, P1) — событие + пользователь: волонтёр, который может сканировать QR
- **Favorite** — пользователь + событие, пара уникальна
- **Comment** — пользователь, событие, текст, дата создания

Правило остаётся прежним: схему Prisma меняет только владелец модели, через PR. Модели `Registration`, `Favorite` и `EventPriorityMember` принадлежат Айжан; `EventStaff` и поля чек-ина в `Registration` добавляет Алдияр через PR, согласовав с Айжан, так как это одна таблица.

## 5. Приоритетная запись («приоритеты посещения»)

Идея: места на популярные события не должны уходить тем, кто записывается и не приходит.

**Статус пользователя**
- Все начинают как `STANDARD`.
- После **3 подтверждённых посещений** (отметка по QR) пользователь становится `ACTIVE`.
- Если пользователь записался, но не пришёл (запись `CONFIRMED` без `checkedInAt` после окончания события), ему добавляется неявка. При **2 неявках** статус возвращается в `STANDARD`, счётчик сбрасывается.
- Числа 3 и 2 вынесены в константы, их можно поменять.

**Приоритетное окно события**
- Организатор задаёт `priorityWindowHours` (например, 24).
- Первые N часов после `registrationOpensAt` записываются только `ACTIVE` и участники из списка `EventPriorityMember`. Остальные видят «Запись откроется для всех в ЧЧ:ММ».
- После окна запись открыта для всех, пока есть места.

**Лист ожидания (P1)**
- Когда мест нет, запись получает статус `WAITLIST`.
- При отмене места первой получает запись из очереди; порядок: сначала приоритетные (`ACTIVE` / список организатора), внутри группы — по времени записи.
- Продвижение очереди и освобождение места выполняются в одной транзакции.

**Что видит пользователь:** бейдж «Активный» в профиле и на карточках записи, понятный текст на кнопке («Записаться», «Приоритетная запись», «Встать в очередь», «Запись откроется в …»).

## 6. Вход на событие по QR

### Как это работает
1. При подтверждённой записи (`CONFIRMED`) система создаёт `qrToken`.
2. Студент открывает «Мои регистрации» и показывает QR на экране телефона.
3. Организатор или волонтёр открывает страницу сканера события и наводит камеру.
4. Сервер проверяет токен и отмечает вход.

### Содержимое QR
Только токен без персональных данных: `registrationId` + подпись HMAC-SHA256 (ключ `QR_SECRET` в переменных окружения). Подделать QR для чужой записи без ключа нельзя.

### Проверки на сервере (`POST /api/checkin`)
- Подпись токена верна
- Запись существует, имеет статус `CONFIRMED` и относится именно к этому событию
- Событие `PUBLISHED`, текущее время внутри окна входа (например, за 60 минут до начала и до конца события)
- Запись ещё не отмечена (повторное сканирование показывает «Уже отмечен в ЧЧ:ММ», а не ошибку)
- Сканирует организатор этого события, его волонтёр или админ

### Ответы сканера (экран организатора)
| Результат | Экран |
|-----------|-------|
| OK | Зелёный: имя студента, «Проход разрешён» |
| Уже отмечен | Жёлтый: время первой отметки |
| Не то событие / нет записи | Красный: «Нет записи на это событие» |
| Вне времени входа | Красный: «Вход ещё не открыт / уже закрыт» |
| Недействительный код | Красный: «Код не распознан» |

После успешной отметки: `checkedInAt` заполняется, `attendedCount` пользователя растёт (это связывает QR с приоритетами).

### Детали
- Сканер должен давать быстрый визуальный ответ (до 1–2 секунд) и звук или вибрацию (P2).
- Камера в браузере работает только по HTTPS (localhost и Vercel подходят).
- P1: ручной ввод короткого кода под QR на случай, если камера не читает.
- P1: защита от перебора (ограничение частоты запросов на `/api/checkin`).
- P2: режим «офлайн-очередь» для плохого интернета на входе.

## 7. Визуальная часть

### 7.1. Общий стиль
- Ощущение: современный молодёжный сервис, светлая тема по умолчанию, много воздуха, крупные обложки событий.
- Акцентный цвет для студентов и организаторов (один, яркий, например индиго или фиолетовый), нейтральные серые для текста и границ.
- Админка визуально отличается: тёмная боковая панель и компактные таблицы, чтобы админ сразу понимал, где находится.
- Семантические цвета: зелёный — успех / пришёл, жёлтый — на модерации / предупреждение, красный — ошибка / отклонено, синий — информация.
- Шрифт: один sans-serif (например, Inter через `next/font`), три размера заголовков, один размер основного текста.
- Скругления и тени едины для всего UI-кита (значения задаёт Даша в `tailwind.config` / CSS-переменных).
- Тёмная тема — P2.

### 7.2. Четыре шаблона (layouts)

**Шаблон 1. Auth** — центрированная карточка с логотипом, без меню. Страницы: вход, регистрация.

**Шаблон 2. Публичный / студенческий** — верхняя шапка (логотип, поиск, ссылки «Афиша», «Избранное», «Мои записи», аватар с меню), контент по центру, футер. На телефоне — нижняя панель навигации. Меню шапки меняется по роли: гостю — «Войти / Регистрация», студенту — его разделы, организатору добавляется «Кабинет организатора», админу — «Админ-панель».

**Шаблон 3. Кабинет организатора** — левая боковая панель: «Мои события», «Создать событие», «Участники», «Сканер»; сверху название выбранного события и быстрые действия. На телефоне боковая панель превращается в выдвижное меню, а «Сканер» всегда доступен одной кнопкой.

**Шаблон 4. Админ-панель** — тёмная боковая панель: «Обзор», «Модерация», «Категории», «Пользователи», «Статистика»; наверху KPI-карточки, ниже таблицы с фильтрами. Приоритет — удобство на десктопе, на телефоне достаточно читаемости.

Каждый шаблон — отдельный Route Group в `app/`, чтобы защита через `proxy.ts` и общий layout накладывались на группу целиком.

### 7.4. UI-кит (делает Даша в первые дни Этапа 1)
Кнопка (варианты: основная, вторичная, опасная, ссылка), поле ввода и select, чекбокс и переключатель, карточка события (в двух видах: сетка и строка), бейдж статуса, модальное окно, выпадающее меню, вкладки, уведомления (toast), пагинация, скелетоны загрузки, пустое состояние, компонент ошибки, таблица, аватар, QR-блок.

### 7.5. Ключевые экраны: что должно быть
- **Афиша:** сверху поиск и фильтры (категория, дата), ниже сетка карточек с обложкой, датой, местом, счётчиком свободных мест и сердечком; внизу пагинация.
- **Страница события:** крупная обложка, блок информации, правая колонка с кнопкой записи и индикатором мест, ниже комментарии. Кнопка меняется по состоянию (запись, приоритетная запись, очередь, «Вы записаны», «Прошло»).
- **Мои регистрации:** список записей, у активной — кнопка «Показать QR», открывающая QR на весь экран с высокой яркостью и названием события.
- **Сканер:** камера на весь экран, цветная полоса результата сверху или снизу, счётчик «пришло N из M».
- **Форма события:** загрузка, ошибки по полям, блок приоритетного окна.
- **Модерация:** таблица очереди с предпросмотром события, кнопки «Одобрить» и «Отклонить» (с полем причины).

### 7.6. Адаптивность и доступность
- Проектируем с телефона (mobile-first), точки: телефон, планшет, десктоп.
- Минимальный размер областей нажатия 44 px, видимый фокус, подписи у полей, достаточный контраст текста.
- Отдельно проверяем на телефоне: страницу события, «Мои регистрации» с QR, сканер.

| **P0** | Ядро: без него нет защиты проекта | Делаем в первую очередь, не переносим |
| **P1** | Важные функции | Начинаем, когда закрыт свой P0 |
| **P2** | Улучшения | Только если остаётся время |

Порядок работы внутри каждого этапа: сначала все P0 команды, потом P1. Если срок горит, P1 и P2 отбрасываем без обсуждения, P0 — никогда.

## 9. Команда (4 человека) и правила работы

| № | Участник | Зона ответственности |
|---|----------|----------------------|
| 1 | Даша | Пользователи и доступ, дизайн-система и шаблоны (layouts) |
| 2 | Алдияр | События, кабинет организатора, сканер и проверка входа по QR |
| 3 | Айжан | Регистрации, избранное, приоритетная запись, QR студента |
| 4 | Даурен | Админ-панель, комментарии, статистика, seed, деплой |

### Как устроены 7 этапов
Работа каждого участника разбита на 7 частей. Одна часть у каждого — это один этап. Правило этапа: **этап закрыт, когда все четверо сделали свою часть и результат можно показать на Vercel**. В конце каждого этапа:
- 5-минутное демо внутри команды по пункту «Что показываем» из раздела 11;
- метка `stage-N` в git на `main`;
- галочки в этом файле уже стоят в pull request'ах каждого участника.

Если у кого-то часть не успевает, этап не растягивается: недоделанное P1 переносится дальше, а P0 добивается всеми вместе в начале следующего этапа.

### Правила работы
- Ветки `feature/<кратко>`, pull request в `main`. Ревью по кругу: 1 → 2 → 3 → 4 → 1.
- Сообщения коммитов: `feat: ...`, `fix: ...`, `docs: ...`, `chore: ...`.
- Схему Prisma меняет только владелец модели, через PR. После merge все применяют миграцию.
- Контракты (`lib/services`, `lib/validators`) меняются через PR с пометкой «контракт» и уведомлением тех, кто их использует.
- Галочки в этом файле ставим в своих pull request.
- Короткая синхронизация команды 2 раза в неделю: что сделано, что мешает, что нужно от других.
